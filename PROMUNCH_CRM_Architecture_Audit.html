PROMUNCH CRM — how the system really works, and what to fix

A full read-through audit of the multi-channel customer platform: a Next.js 16 dashboard fronting 48 Supabase Deno edge functions, Postgres, and live integrations with Meta WhatsApp, Instagram, Shopify, Amazon, Gmail and Slack. This document maps the real backend, then ranks what needs hardening for a reliable production startup.

Audited 2026-07-02 · repo promunch-crm @ main · ~18.7k lines frontend / ~14.7k lines edge functions · 2 criticals verified live criticals fixed in code · pending deploy

01 Executive Summary

The product is genuinely impressive for its size: one owned system replacing Klaviyo + a WhatsApp BSP + manual ops, with real durability engineering on the money-critical paths (message dedup, atomic send locks, dead-letter queues, reconciliation sweeps). The gap is security posture and operational reproducibility — the same corners cut to ship fast now expose live customer PII and paid-send endpoints to the open internet.

What's strong keep

  • Money paths are idempotent: wa_messages unique constraints, atomic per-order/per-turn claim tables, per-campaign send lock — the 86-customer and 195-duplicate incidents were fixed structurally at the DB, not patched in app code.
  • Durable job queues (wa_jobs/ig_jobs) with backoff + dead-letter, plus reconciliation sweeps and health watchdogs — inbound work is rarely silently lost.
  • Middleware fails closed on /api/*: every dashboard route needs a session; only webhooks + cron are exempt (and self-verify).
  • Shared code is mostly centralized: one service-role client used by 38 functions; a single alerting module used by 24.

What's urgent fix now

  • Public anon key reads & writes all customer PII — verified: dumped real names, emails, phones from contacts + orders live.
  • service_role key is in git history and never rotated — the leaked key still matches the active .env.local key. God-mode over the DB.
  • Paid-send edge functions (wa-send, wa-campaign-send, ig-send, wa-ai-reply) are internet-callable with no auth.
  • The Next.js Shopify webhook does zero HMAC verification; several webhook/cron secrets fail open when unset.

03 High-Level Architecture

Three tiers. The Next.js app is a thin dashboard + API proxy; the real logic lives in Deno edge functions triggered by webhooks and cron; Postgres is the shared source of truth and the coordination layer (locks, claims, queues all live in tables).

Tier 1 — Dashboard

Next.js App Router. Server + client components. Talks to Postgres two ways: server API routes with the service-role key (bypassing RLS, ~50 routes), and client components with the anon key (RLS-dependent).

Tier 2 — Edge functions

The actual product logic. Triggered by provider webhooks, cron, and function-to-function calls. Each domain mirrors the same shape: webhook → enqueue job → AI reply → send chokepoint → ledger.

Tier 3 — Postgres

Not just storage — it's the coordination substrate. Locks, atomic claims, dedup constraints, and job queues are all tables, which is why the money paths are correct under concurrency.

04 How a Request Actually Moves

Two representative paths — an inbound WhatsApp message and a marketing broadcast — show the "webhook → queue → AI → chokepoint → ledger" spine that every channel reuses.

Inbound WhatsApp support message

Customer texts the business number │ ▼ Meta Graph POST (X-Hub-Signature-256) wa-webhook — verify HMAC → dedup on wa_message_id → upsert wa_thread/wa_message │ if thread.status == 'bot': ├──▶ wa-ai-reply (fast path, best-effort) → claim_ai_reply (atomic per-turn) │ → stuff Master KB into prompt → OpenAI │ → tool: lookup_order / request_order_change │ → wa-send (single outbound chokepoint) → records wa_message → Meta └──▶ enqueue wa_jobs(kind=ai_reply) ← backstop if fast path failed │ ▼ cron ~1 min wa-jobs-tick — drains queue, backoff, dead-letters after max_attempts
Why this is well-built: the fast path is for UX latency, but correctness is guaranteed by the enqueued job. The atomic claim_ai_reply means two workers can't double-reply to the same turn, and wa-send is the one place every outbound send is recorded + failure-alerted.

Marketing broadcast (the incident-hardened path)

Staff schedules a campaign in the dashboard │ ▼ pg_cron every ~2 min wa-campaign-worker — promotes scheduled→sending, acquires per-campaign send_lock │ ▼ wa-campaign-send — for each opted-in contact: guard: partial-unique (campaign_id, contact_id) WHERE status in (queued,sent,delivered,read) → personalize (Claude) → Meta template send → wa_message row │ ▼ wa-campaign-report — recount from wa_messages → Slack card
The one weak seam: wa-campaign-send does not route through the guarded wa-send chokepoint, so campaign failures rely on a separate alert path — which previously had an arity-mismatch bug in one of the three postSlack helpers. The dedup itself is now structurally safe (DB-enforced), which is what stopped the 195-duplicate Edamame incident.

06 Data Model & RLS Posture

The schema is split across two migration directories — a 3-file legacy set at the repo root (contacts, orders, campaigns) and a 45-file set in promunch-email-agent/ (everything WhatsApp / Shopify / Amazon / IG / B2B). This split is the root of the security inconsistency below.

Idempotency machinery exemplary

  • wa_messages.wa_message_id UNIQUE — inbound dedup
  • partial UNIQUE (campaign_id, contact_id) — structural anti-duplicate for broadcasts
  • wa_campaigns.send_lock_at — per-campaign single-sender lock
  • claim_order_confirmation() / claim_ai_reply() / claim_ig_reply() — atomic per-entity claims with steal windows
  • amazon_finance_events.dedup_key UNIQUE — re-poll safe

Gaps & smells

  • wa_journey_runs has no DB-level uniqueness on (journey_key, order_ref) — journey idempotency is app-only
  • Unindexed hot-path columns: wa_link_clicks.contact_id, outreach_events.resend_email_id
  • 5 duplicate migration timestamps → ambiguous apply order
  • Evidence of in-place migration edits (defensive re-adds) → environments may hold different subsets
  • recompute_wa_rfm_tags() is SECURITY DEFINER with no pinned search_path

RLS / anon-key exposure — inconsistent

I verified this live against production using the public anon key. The newer promunch-email-agent tables are correctly locked (anon has no grant → 42501 permission denied). The legacy root tables are wide open.

TableAnon access (verified live)Verdict
contactsFull read + write — returned real name/email/phoneExposed

Verified: GET /rest/v1/contacts?select=* with the browser-shipped anon key returned live customer PII (e.g. a real name, gmail.com address, and +91… phone). The orders table is equally open. This is a reportable data breach exposure, not a theoretical one. The fix is to drop the USING(true) anon policies on the legacy tables and route all access through server API routes — matching how the newer tables were already secured.

07 Reliability Engineering

This is the strongest part of the system and worth calling out — the durability patterns are more disciplined than most startups at this stage. The weaknesses are localized, not structural.

Strong Self-healing spine

  • Durable queues: wa_jobs/ig_jobs with backoff + dead-letter to human after max attempts
  • Reconciliation sweeps: wa-confirmation-sweep diffs shopify_orders vs sent; gmail-poll re-picks unread; order backfill as webhook backstop
  • Watchdogs: wa-health heartbeat → wa-watchdog dead-man's-switch alerts if beats stop
  • Single send chokepoints record every send + Slack-alert failures with decoded Meta error codes

Weak Silent-failure pockets

  • amazon-poll (496 lines, 3 pipelines) — 5 swallow-and-retry catches, no connector-log alerting; a permanently-failing item never surfaces
  • KB pipeline & Shopify backfills have no structured alerting either
  • Slack-post failures degrade to console.warn only — if Slack is the failing dependency, alert visibility drops to logs
  • Backfill functions page entire history with no pagination-resume guard — a large run can be killed mid-page
  • WA_SKIP_SIGNATURE / IG_SKIP_SIGNATURE env flags can disable HMAC verification entirely

09 Tech Debt & Optimization

Maintainability

  • 2,540-line dashboard/whatsapp/page.tsx and 1,305-line leads page — split into feature components + hooks
  • 1,029-line wa-ai-reply monolith — extract triage / tools / ticketing / KB modules
  • Zero tests across the whole app — the money paths especially need coverage
  • 3× postSlack, 2× send libs, 3× updated_at triggers — consolidate

Frontend / performance

  • No data-fetching library (React Query/SWR) — manual fetch + state in giant client components
  • No shared state manager; prop-drilling in the mega-pages
  • Next.js 16: migrate middleware.ts → proxy.ts; adopt Cache Components + next/image
  • 3.7 MB edmame-wa-campaign.mp4 + redesign HTML artifacts committed to the repo root

Operational reproducibility

  • Schema split across 2 migration dirs; cron across 3 systems (some dashboard-only)
  • Migrations applied by hand ("Run ONCE in SQL editor") → environment drift risk
  • 5 duplicate migration timestamps → non-deterministic apply order
  • Move all pg_cron definitions + the legacy tables into versioned migrations

Architecture consistency

  • Two auth styles: leads/* + instagram/* double-check the session; the larger whatsapp/* surface relies on middleware only
  • No RBAC — "everyone gets full access" (fine at 3 people, a liability as the team grows)
  • wa-campaign-send bypasses the wa-send chokepoint — unify the send path
  • god-table shopify_orders patched by 5 migrations (status + ~30 attribution cols + creator flag)

10 Prioritized Remediation Roadmap

Ordered by risk-reduction per hour of work. The first three are same-day and stop active exposure; the rest harden the platform toward production-grade.

Rotate the service_role key & purge git history ~1 hr C2

Rotate in Supabase, update .env.local + Vercel/Supabase secrets, then BFG/git-filter-repo the value out of history and force-push. Remove secrets from .claude/settings.json.

Lock the legacy anon RLS policies ~1 hr C1

Drop USING(true) anon policies on contacts/orders/campaigns/flows/email_events; move them to service_role-only, matching the newer tables. Verify with the anon-key curl test.

Authenticate the send + worker functions ~2 hr C3 · H3 · M3

Add one shared-secret Bearer check helper; apply to wa-send, wa-campaign-send, ig-send, wa-ai-reply, and the tick/worker functions. Stops arbitrary paid sends and AI-spend abuse.

Fix webhook/cron trust ~2 hr C4 · H4 · H5

Add real HMAC to the Next Shopify route; make every webhook/cron secret fail closed when unset; remove the WA_SKIP_SIGNATURE bypass from prod.

Constrain order lookup & sanitize filters ~2 hr H1 · H2

Scope lookup_order to the chatter's phone; whitelist order numbers to digits; replace string-built .or() with discrete .eq()/.in().

Add rate limiting + security headers ~half day M1 · L3

Per-IP/key limits on public functions and API routes; a CSP/HSTS/X-Frame-Options block in next.config.ts.

Reproducible ops: consolidate cron + schema ~1 day debt

Move all pg_cron jobs and the legacy tables into versioned migrations; fix duplicate timestamps; document the one-schema source of truth. Add alerting to amazon-poll + backfills.

Refactor + test the money paths ongoing quality

Break up the 2,540-line page and 1,029-line function; consolidate the 3 postSlack helpers; add tests around dedup/claims/send. Introduce RBAC before the team grows. Adopt React Query for the dashboard.

Bottom line: the hard part — a correct, self-healing, multi-channel backend — is already built and genuinely good. The remaining work is almost entirely access control and reproducibility, and the four highest-risk items are each a few hours. Do the top three today, and this moves from "impressive but exposed" to "production-grade for a reliable startup."
