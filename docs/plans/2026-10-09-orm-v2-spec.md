## 1. Reputation Score (shared formula, identical on both sides)

Implemented twice as a pure function with the SAME test vectors: `src/lib/orm/score.ts` and `promunch-email-agent/supabase/functions/_shared/orm-score.ts`.

Input: relevant (relevant is not false) AND enriched mentions in the period.

| Part | Weight | Value 0-100 | Missing when |
|---|---|---|---|
| Rating | 0.40 | `(avg(rating) - 1) / 4 * 100` over mentions with a rating | no rated mentions |
| Net sentiment | 0.30 | `(pct_pos - pct_neg + 100) / 2` where pos = sentiment > 0, neg = sentiment < 0 | no scored mentions |
| Reply rate | 0.20 | negatives handled / negatives * 100. Handled = status in (replied, ignored) OR case_status = resolved | no negatives → 100 |
| Critical | 0.10 | `max(0, 100 - 50 * open_critical)`; open = urgency critical AND status not in (replied, ignored) AND case_status is distinct from resolved | never missing |

Missing parts are dropped and the remaining weights re-normalised. Score = round(weighted mean). Return `{ score, parts: { rating, net_sentiment, reply_rate, critical }, net_sentiment_raw (-100..100), avg_rating, counts }`. Bands for copy: 85+ "Excellent", 70-84 "Good", 50-69 "Needs work", <50 "At risk".

Test vectors (both suites): empty → score null; one 5★ positive → 100; mixed fixture → exact expected numbers written in the test.

## 2. Overview (UI + `/api/orm/summary` extension)

`GET /api/orm/summary?days=7|30|90` adds (keep existing fields):
- `score` (formula above, current period) and `score_prev` (same length period before) and `score_weekly`: last 12 IST weeks `[{ week_start, score, mentions }]` (each week computed from that week's mentions; null when empty).
- `products`: per `product` label `[{ product, mentions, avg_rating, rated, pct_negative, top_complaint_topic, trend: 'up'|'down'|'flat' (avg rating this period vs previous) }]`, worst first (pct_negative desc, then avg_rating asc), null product grouped as "Not sure which product".
- `drivers`: per topic `{ topic, praise, complaints, neutral }` (sentiment > 0 / < 0 / = 0), sorted by praise+complaints desc, top 10.
- `response`: `{ open_negatives, open_critical, median_reply_hours (replied_at - coalesce(posted_at, collected_at)), oldest_unanswered_days, reply_rate, cases: { open, in_progress, resolved, recovered, recovery_rate } }`.
- `channels`: per source `{ key, label, avg_rating, reviews, star_mix: {1..5}, weekly: [{ week_start, avg_rating, count }] (12 weeks) , velocity_per_week (last 4 weeks avg) }`.
- `competitors`: latest snapshot per ASIN from `orm_competitor_snapshots` + our own top ASIN ratings (is_ours) for side-by-side.

Overview layout, top to bottom (4 questions):
1. **How are we doing?** Big score with band word and change vs previous period, 12-week score sparkline, then one hairline row: net sentiment, avg rating, reply rate, open critical.
2. **Where is it going wrong?** Product scorecard table (phone: two-line rows): product, avg rating with stars, reviews, % negative as coloured text, top complaint, trend arrow. Worst first.
3. **What do people love vs hate?** Diverging horizontal bars per topic: complaints to the left (negative colour), praise to the right (positive colour), shared zero axis, counts at bar ends.
4. **Are we on top of it?** Response row (open negatives, median reply time, oldest unanswered, recovery rate), then per channel: weekly rating line or bars (12 weeks) + star mix (5★ to 1★ thin bars) + reviews per week. Competitor block (only when snapshots exist): our rating vs each competitor, review counts.

Each KPI has a one-line plain-English explanation on hover/tap ("Reply rate: share of negative mentions we answered or closed").

Charts: load the `dataviz` skill before writing chart code and follow it (palette, marks, accessibility, light/dark). Plain SVG/CSS is fine; no new chart dependency unless the repo already has one (check package.json).

## 3. Complaint cases (C)

- Edge (`orm-tick` ENRICH step): when `orm_settings.auto_case_on_negative` and a newly enriched relevant mention has sentiment < 0 OR intent = complaint OR urgency in (critical, high) → set `case_status = 'open'`, `case_opened_at = now()` (only if case_status is null).
- API `PATCH /api/orm/mentions/[id]` accepts `case_status`, `case_outcome` (required when case_status = resolved), `assignee`; stamps `case_resolved_at` when resolved, clears it when reopened.
- Drawer: a "Case" section: status (Open / In progress / Resolved), owner, outcome picker on resolve, customer + order link when matched, "Message on WhatsApp" link to the existing inbox thread when the contact has a wa_thread (read-only link, never sends).
- Feed: a "Cases" filter chip (open + in progress).
- One-off backfill in the migration rollout: open cases for existing negatives from the last 30 days (run by the deployer, not in the migration).

## 4. Judge.me replies (E)

Verify Judge.me's API supports posting a public reply to a review (docs: judge.me/api). If YES: `POST /api/orm/mentions/[id]/reply` (session, `requireUser`) → for source judgeme only: insert-first `orm_reply_claims` (23505 → 409 "already replied") → call Judge.me with `JUDGEME_API_TOKEN` via `getSecret` → on success set status replied, reply_text, replied_at/by, reply_channel 'judgeme_api', reply_external_id; on failure mark claim failed (retry allowed only via an explicit "Try again" that deletes a FAILED claim). Drawer shows "Post reply on the website" for Judge.me mentions with a confirm dialog ("This posts publicly under PROMUNCH"). If NO API support: keep copy-and-open and note it in the report.

## 5. Weekly WhatsApp digest (A) and spike alerts (B): edge `orm-tick`

- DIGEST step (after ALERT): when `weekly_digest_enabled`, IST day-of-week = `weekly_digest_dow` and IST hour ≥ `weekly_digest_hour_ist`: claim `orm_digest_log(week)` insert-first (same CAS + `wa_messages` ledger pattern as influencer-tick's digest; `sent_by = orm_digest:<week>:<wa_id>`). Content via `ops_ticket_alert` template vars: 1 "PROMUNCH reputation, week of <date>", 2 "Score <n> (<band>), <+/-d> vs last week", 3 "<mentions> mentions · <avg>★ · <pct neg>% negative", 4 "Worst: <product> <avg>★", 5 "Top complaint: <topic>. Open cases: <n>. <link to /dashboard/reputation?tab=overview>" (≤300 chars each). Empty week → `skipped_empty`. Recipients = alert recipients.
- SPIKE step: when `spike_alerts_enabled`: group relevant negative mentions in the last `spike_window_days` by (product, topic); any group with count ≥ `spike_threshold` → claim `orm_spike_log(key)` where window start = floor to the window (so one alert per group per window) → one WhatsApp to the alert recipients: "Possible batch issue: <n> complaints about <topic> on <product> in <days> days". Ledger marker `orm_spike:<key>:<wa_id>`.
